这次最值得关注的结论是：**`infra` 的问题不只在多线程同步，还在于一些接口授予了调用者实际上并不具备的内存访问权限。部分问题在单线程、安全 Rust 调用中就能触发。**

先限定范围：这份结果针对审计时的 **main `7e124fa98`**，不包含我们其他分支上的基础设施改造。113 项原有测试在宿主全部通过；加上 16 项契约测试后，Miri 两种模型分别报告 56、49 项 UB。**这些是失败用例数，不是独立缺陷数**，不少失败来自同一个底层操作。[完整汇总](/home/hegui/vivoblueos/infra-main-miri-audit/kernel/infra/evidence/2026-11-06-main-miri/summary.md)

我会按下面几类理解它们。“严重程度”指修复优先级和契约破坏程度，并不是已经评估过可利用性的安全漏洞评级。

| 类别 | 代表问题 | 我的判断 |
|---|---|---|
| 分配与初始化契约 | 空指针切片、零大小裸分配、读取未初始化字节 | 高优先级，证据明确，通常能局部修复 |
| 安全接口允许冲突访问 | `NoLock`、侵入式锁向外投影整个对象 | 高优先级，需要调整访问契约 |
| 线程安全保证不成立 | `TinyArc` 无条件 `Send/Sync`、`NoLock` 跨线程写 | 高优先级，需要核查类型约束和实际同步 |
| 内部可变性表示错误 | `TinyArcCas` 将普通字段强转成原子字段 | 高优先级，表示与访问方式需要重新设计 |
| 侵入式容器别名问题 | 链表、侵入式堆、部分树操作 | 影响广、改造较难，需要分层处理 |
| 测试自身问题 | 未回收的 `Box::leak`、部分 unsafe 用法 | 单独修复，不能全部归责于生产算法 |
| 模型差异及运行成本 | 红黑树仅 Stacked 失败、长测试超时 | 需要继续分析，不能直接等同于确定的生产故障 |

**一、分配到的内存，不等于已经存在合法的值。**

main 上的 `Storage` 混淆了几个状态：

- 没有内存的空状态；
- 成功分配的零大小状态；
- 已分配、但尚未初始化的字节；
- 可以作为 `[u8]` 读取的已初始化字节。

例如，长度为零并不能允许用空指针构造 Rust 切片引用；裸分配接口也有自己的非零大小前提。另一方面，`u8` 接受所有**已初始化的位模式**，并不意味着可以读取未初始化内存。

更直接的问题是，公开的 `Storage::Alloc` 变体允许安全代码构造一个无效所有者，随后在析构中触发非法操作。这说明内部不变量没有被类型边界保护起来。

`BoxedRingBuffer` 则继承了初始化问题：writer 暴露 `&mut [u8]`，而这个类型既允许写，也允许读。调用者遵守唯一 writer 的约定，仍然可以读到尚未初始化的字节。

这些问题正好解释了为什么此前要做 Storage 表示封闭、初始化契约和自有缓冲区初始化。**未初始化分配本身完全合理，问题在于过早提供可读取的接口。**

**二、`NoLock` 的问题，比“多线程时没上锁”更基础。**

`NoLock::try_write` 总能获得写守卫。如果安全调用者可以取得两个守卫，并交错使用它们产生的可变引用，就破坏了独占访问规则。读守卫和写守卫重叠也有类似问题。

这在单线程就能发生，因此：

> “这个配置只有一个 CPU”不能证明“此时只有一个有效的可变引用”。

单线程还可能存在嵌套调用、重入，以及同时保留多个守卫。当前 `Sync` 实现又把问题扩展到了真正的跨线程数据竞争。

所以不能仅靠补一个 `!Send` 或限定单核来解决。需要明确：独占性究竟由运行时借用检查、外部执行上下文，还是某种无法重复取得的权限凭证保证。

**三、侵入式锁的问题，是锁住了字段，却承诺了整个对象的独占访问。**

`INoLock`、`IRwLock` 会从嵌入的锁字段恢复外围对象的 `&mut T`。

问题在于，调用者可能已经持有外围普通字段的 `&field`。获得锁，并不会撤销这个引用，也不会自动把外围普通字段变成 `UnsafeCell` 内部的数据。

新增测试特意保证了：

- 外围对象一直存活；
- 地址没有移动；
- 偏移计算正确。

仍然能够复现冲突。这说明此处的主要问题是**访问权限**，不能用 Pin 或修正偏移解决。即使锁确实互斥，也需要保证所有受保护数据都通过相应的访问边界取得。

**四、`TinyArc` 的引用计数安全，不能替 payload 提供线程安全。**

main 的 `TinyArc<T>` 无条件实现 `Send/Sync`，使得 `TinyArc<Cell<i32>>` 能被安全地共享到不同线程。两个线程通过 `Cell` 写同一位置，就出现数据竞争。

这里要分清两件事：

- 原子引用计数可以协调所有者的数量；
- 它不会协调内部值的读写。

这是相当明确的类型约束问题。但修复时也不能看到某个调用者编译不过，就给其内部类型补一个 `unsafe impl Sync`；编译失败可能恰好暴露了此前被掩盖的设计缺口。

另外，一些并发链表测试调用 `get_mut_unchecked` 时仍有其他所有者。该函数内部又创建整个 `TinyArcInner<T>` 的可变引用，覆盖了引用计数字段。相关诊断需要同时审查 **unsafe 调用是否满足前提**和**辅助函数创建的引用是否过宽**，不能全部算作链表并发算法错误。

**五、原子操作不能补救不合法的内部可变性表示。**

`TinyArcCas` 保存的是普通 `Option<TinyArc<T>>`，然后把它的地址转成原子指针引用，执行 CAS 或 swap。

关键问题是：**指针转换不会凭空赋予通过共享引用修改普通字段的权限。**

即使生成的是原子指令、内存排序也正确，Rust 层面的存储表示仍可能不合法。这类修复不能只改 ordering；需要从真正的原子存储、所有权转移和回收规则一起设计。已有 CAS/swap 测试就在两种模型中复现了问题。

**六、侵入式容器的问题最成体系，也最容易被“地址没变”误导。**

链表、侵入式堆中的常见模式是：

1. 从一个引用取得裸指针并保存；
2. 后续又为同一对象或外围对象建立新的引用；
3. 再通过之前保存的指针访问。

**指针数值没变、对象还活着，不代表这个访问方式仍然合法。** 新的独占借用、共享整个外围对象等操作，可能与旧访问路径冲突。

这也解释了为什么：

- 外层加锁后仍可能失败；
- 节点放到堆上后仍可能失败；
- 引入 Pin 后仍可能失败；
- 将链接字段换成原子字段后，仍不能随意取得整个节点的 `&mut`。

这些容器需要分别证明地址稳定、生命周期、链接修改权限和 payload 访问权限。许多 `TinyArcList`、排序链表的失败实际来自它们依赖的底层链表，因此应该先修底层契约，避免逐个上层测试打补丁。[具体根因记录](/home/hegui/vivoblueos/infra-main-miri-audit/kernel/infra/MIRI_AUDIT.md)

**还有两类结果需要克制解读。**

红黑树的五项失败只出现在 Stacked Borrows，Tree Borrows 下通过。这里存在具体的“先借用可变节点、再共享外围对象、然后继续写节点”的模式，但两种模型对借用的处理不同。应保留为待分析问题，不能因为一种通过就宣布安全，也不能仅凭另一种失败断言已经发生生产内存破坏。

两项泄漏则明确来自测试中的 `Box::leak` 没有回收，不是“链表所有操作都泄漏”的证据。唯一超时测试提高时间上限后通过，只是 Miri 执行成本较高。

**我的处理顺序会是：先关闭安全 API 可以直接触发 UB 的入口，再处理容器内部的访问模型。**

具体是先处理 Storage/缓冲区初始化、`TinyArc` 的线程约束、`NoLock` 和锁投影；然后单独设计 `TinyArcCas`，再从一个最小侵入式链表开始建立可复用的节点契约。红黑树的模型差异另列调查，测试泄漏可以独立清理。

这次最有价值的发现，是原有功能测试没有覆盖的一些契约漏洞：原有 ringbuffer、NoLock 和普通读写锁测试都能通过，但针对“接口允许调用者做什么”新增测试后就暴露了问题。后续测试应继续围绕这些边界展开，而不只是增加压力测试次数。
